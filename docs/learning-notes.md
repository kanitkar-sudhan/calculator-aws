## 1. Project overview

This is a **calculator that runs entirely in the browser**, built with React, Vite and TypeScript. It's hosted on AWS as static files in a private S3 bucket, served through CloudFront. All the math runs in the browser, so there's no backend or API. The AWS setup is written as code with AWS CDK (TypeScript).

```
calculator-aws/
├── package.json          Root scripts that run commands in web/ and infra/
├── README.md             Setup, dev, deploy and cost notes
├── Dockerfile            Optional local dev/build container
├── docker-compose.yml    Runs the dev server in Docker
├── .dockerignore / .gitignore
├── web/                  The calculator app
└── infra/                AWS infrastructure (CDK)
```

### Root files

- **[package.json](../package.json)** runs commands in the subfolders: `dev`, `test`, `build`, `synth`, `deploy` (builds, then runs `cdk deploy`), `destroy`, `install:all`, `docker:dev` and `docker:build`. It has no dependencies of its own.
- **[Dockerfile](../Dockerfile)** builds in stages:
  - `deps` installs packages.
  - `dev` runs a hot-reloading Vite server.
  - `builder` and `build` produce `web/dist` from a fixed Node 24 image.

  It's for local use only. Nothing runs in a container on AWS.
- **[docker-compose.yml](../docker-compose.yml)** runs the `dev` stage on port 5173 and mounts `web/` so edits reload live.

### How the pieces fit

`npm run build` creates `web/dist/`. `npm run deploy` then uploads it to S3, and CloudFront serves it at `https://<id>.cloudfront.net` (or at your custom domain).

`web/dist/`, `infra/cdk.out/` and the two `node_modules/` folders are all generated and can be rebuilt.

## 2. The `infra/` folder

Nothing in `infra/` runs while people use the calculator. CloudFront serves the built files from S3, and that's all. `infra/` is only used when you deploy, update or delete the AWS resources.

There are three kinds of content in it:

- **Source:** files you write and keep.
- **Generated by install:** created by `npm install`.
- **Generated by synth:** created by `cdk synth`. `cdk deploy` runs synth first, so it creates these too.

[.gitignore](../.gitignore) already excludes `node_modules/` and `cdk.out/`, which matches this split.

| Path | Kind | Purpose | Lifetime |
| --- | --- | --- | --- |
| [bin/](../infra/bin/) | Source | Starting point of the CDK app | Keep; needed to deploy |
| [lib/](../infra/lib/) | Source | Defines the AWS resources | Keep; needed to deploy |
| [cdk.json](../infra/cdk.json) | Source (config) | Tells the CDK tool how to run the app | Keep; needed to deploy |
| [package.json](../infra/package.json) | Source (config) | Dependencies and npm scripts | Keep; needed to deploy |
| [package-lock.json](../infra/package-lock.json) | Generated by install, but treat as source | Pins exact dependency versions | Keep and commit |
| [tsconfig.json](../infra/tsconfig.json) | Source (config) | TypeScript compiler settings | Keep; used for type-checking and the editor |
| `node_modules/` | Generated by install | Installed packages (~240 MB) | Temporary; restore with `npm install` |
| `cdk.out/` | Generated by synth | Output that `cdk deploy` uploads (~22 MB) | Temporary; rebuilt on every synth or deploy |

### Source files

**[bin/infra.ts](../infra/bin/infra.ts)** is the entry point. It creates the CDK app and reads the optional `-c domainName=… -c hostedZoneId=…` settings. If only one of the two is given, it stops with an error. It then creates one `CalculatorSiteStack` in us-east-1.

**[lib/calculator-site-stack.ts](../infra/lib/calculator-site-stack.ts)** is the actual infrastructure definition. Most infra changes happen here. It creates:

- a private, encrypted, HTTPS-only S3 bucket that only CloudFront can read (via Origin Access Control)
- a CloudFront distribution that redirects HTTP to HTTPS and returns `index.html` for missing pages (403/404)
- an upload step (`BucketDeployment`) that copies `web/dist` to the bucket and clears CloudFront's cache on every deploy
- if a custom domain is given, an ACM certificate and a Route 53 DNS record
- the outputs `SiteUrl`, `DistributionDomainName`, `DistributionId` and `BucketName`

**[cdk.json](../infra/cdk.json)** has two jobs:

- `"app": "npx tsx bin/infra.ts"` tells the CDK tool how to run your code. `tsx` runs the TypeScript directly, so no `.js` files are ever compiled into the project.
- The `context` block turns on a few CDK feature flags, such as `useOriginAccessControl`. Some of these change what gets generated, so keep it.

**[tsconfig.json](../infra/tsconfig.json)** holds TypeScript settings for `bin/` and `lib/`, with `cdk.out` excluded. `tsx` runs the code directly, so this file is used only by `npm run typecheck` (`tsc --noEmit`) and by your editor. It sets `declaration: true`, but that has no effect because nothing compiles files to disk.

**[package.json](../infra/package.json)** lists:

- **Dependencies:** `aws-cdk-lib` (the AWS building blocks) and `constructs`.
- **Dev dependencies:** the `aws-cdk` command-line tool, `tsx`, `typescript` and `@types/node`.
- **Scripts:** `synth`, `diff`, `deploy`, `destroy`, `bootstrap` and `typecheck`.

**[package-lock.json](../infra/package-lock.json)** is written by npm, but you commit it like source. It makes every install pick exactly the same versions.

### Generated: `node_modules/`

This holds the installed packages, which synth and deploy need. You can delete it and restore it with `npm install`. On this machine, a plain `npm install` fails because npm's cache is owned by root, so use `npm install --cache <dir>`.

### Generated: `cdk.out/`

Synth turns your TypeScript into these files. `cdk deploy` uploads them to the staging bucket that CDK creates during bootstrap, and CloudFormation builds the resources from them. You can delete them at any time; the next synth recreates them.

| File | Purpose |
| --- | --- |
| `CalculatorSiteStack.template.json` | The CloudFormation template, which is what actually gets deployed |
| `CalculatorSiteStack.assets.json` | Lists the local files to upload and where in the staging bucket each one goes |
| `manifest.json` | Index of everything in `cdk.out`, plus the IAM roles the deploy will use |
| `CalculatorSiteStack.metadata.json` | Maps template resources back to your source code, for clearer error messages |
| `tree.json` | Tree of the resources your code created (used by tools and the console) |
| `validation-report.json` | Policy-check results; empty here because no validation plugins are set up |
| `cdk.out` | Just the output format version (`{"version":"54.0.0"}`) |

The `asset.<hash>` entries are files that get uploaded during deploy:

| Asset | What it is | When it runs |
| --- | --- | --- |
| `asset.0184b4…/` | A copy of `web/dist`, i.e. your built calculator | Uploaded to the site bucket and served to visitors. It's the only part of `cdk.out` that users ever see. |
| `asset.35328d…/index.py` | Python code for a Lambda (a small AWS function) that copies the site into S3 and clears CloudFront's cache | Runs during each deploy |
| `asset.98f62b….zip` (22 MB) | A Lambda layer containing the AWS CLI, which the upload Lambda uses | Used by that upload Lambda during deploy |
| `asset.faa95a…/index.js` | A Lambda that empties the bucket so it can be deleted (added because of `autoDeleteObjects: true`) | Runs only on `npm run destroy`, or when the bucket is replaced |

The hashes come from each file's contents. When you change and rebuild `web/`, you get a new `asset.<hash>` folder, and older ones can pile up. `manifest.json` shows the account as `unknown-account`, which means the last synth ran without AWS credentials. That's normal for a synth.

### How it flows

`npm run deploy` (at the project root) does three things:

1. Builds the site into `web/dist`.
2. Runs `cdk synth`, which uses `tsx` to run `bin/infra.ts` and `lib/calculator-site-stack.ts` and writes `cdk.out/`.
3. Runs `cdk deploy`, which uploads the assets and has CloudFormation create or update the stack.

After that, visitors' browsers get the files from CloudFront, which reads them from S3. No CDK code is involved at that point.

### Generated: `dist/`

| File | Purpose |

## 5. `.ts` vs `.tsx`

Both are TypeScript. The difference is that a **`.tsx` file can contain JSX**, the HTML-like syntax React uses to describe the UI:

```tsx
return <button onClick={...}>{key.label}</button>;   // JSX — only allowed in .tsx
```

JSX isn't JavaScript. The build turns each tag into a function call; with this project's `jsx: react-jsx` setting, `<button …>` becomes roughly `jsx('button', {...})`. JSX is only allowed in `.tsx` because `<Type>value` is also an older TypeScript cast syntax, and the two can't be told apart.

The convention in this project:

- **`.tsx`** for files that render UI: `main.tsx`, `App.tsx`, `Calculator.tsx`
- **`.ts`** for plain logic with no UI: `calc.ts`, `calc.test.ts`

## 6. Application logic flow in `web/src`

### How the files depend on each other

```
index.html
  └─ <script src="/src/main.tsx">
       main.tsx  ── imports ──► App.tsx, styles.css
         App.tsx ── imports ──► Calculator.tsx
           Calculator.tsx ── imports ──► calc.ts  (reduce, initialState, types)

calc.test.ts ── imports ──► calc.ts   (tests only; never loaded by the browser)
```

Imports only go downward. `calc.ts` imports nothing from the project and knows nothing about React, the page or the keyboard.

### Phase 1: Startup (runs once)

1. **[index.html](../web/index.html)** loads with an empty `<div id="root">`. Its script tag loads `main.tsx`; in a production build, it loads the bundled JS file instead.
2. **[main.tsx](../web/src/main.tsx)**:
   - imports `styles.css`, which applies the styles
   - finds `#root`, and throws an error if it's missing
   - runs `createRoot(container).render(<StrictMode><App /></StrictMode>)`, which hands that `<div>` over to React

   This file runs once and isn't involved after startup.
3. **[App.tsx](../web/src/App.tsx)** returns the page layout: a `<main>` with a heading, `<Calculator />` and a hint paragraph. It holds no state, so it never changes after the first render.
4. **[Calculator.tsx](../web/src/Calculator.tsx)** sets things up on its first render:
   - `useReducer(reduce, initialState)` creates the state from `calc.ts`'s `initialState`, which is `{display: '0', accumulator: null, pendingOp: null, overwrite: true, error: false}`. It returns two things:
     - **`state`**: the current values
     - **`dispatch`**: the function you call to request a change
   - `useEffect` adds a `keydown` listener to `window` so the keyboard works anywhere on the page. It returns a function that removes the listener when the component goes away.
   - It returns JSX: an `<output>` showing `state.display`, and 19 `<button>`s generated from the `KEYS` table.

### Phase 2: Each key press (repeats)

```
mouse click on a button ─► onClick={() => dispatch(key.action)} ─┐
                                                                  ├─► dispatch(action)
key press ─► handleKeyDown ─► actionForKey(event.key) ────────────┘        │
                                                                           ▼
                                        React calls calc.ts: reduce(state, action) → newState
                                                                           │
                                        React re-renders Calculator with newState
                                                                           │
                                        <output> now shows newState.display
```

- An **action** is a small object describing what was pressed, such as `{type: 'digit', value: '7'}` or `{type: 'op', value: '+'}`. The `Action` type in `calc.ts` lists every possible action.
- **`actionForKey`** turns keyboard keys into actions: `Enter` becomes `equals`, `Escape` becomes `clear`, `x` becomes `*`, and so on.
  - It ignores key combinations that use Cmd, Ctrl or Alt, so browser shortcuts keep working.
  - It calls `preventDefault()` so that, for example, `/` doesn't open the browser's quick-find.
- **`reduce`** makes all the decisions. It takes the current state and an action and returns a **new** state object, without changing the old one or touching the page. Because the result is a new object, React sees the change and re-renders.

### Example: `7 + 3 =`

The `overwrite` flag means "the next digit starts a new number instead of being added to the current one".

| Key | `reduce` branch | display | accumulator | pendingOp | overwrite |
| --- | --- | --- | --- | --- | --- |
| (start) | `initialState` | `0` | null | null | true |
| `7` | `digit`: overwrite is on, so replace | `7` | null | null | false |
| `+` | `op`: nothing pending, so store 7 | `7` | 7 | `+` | true |
| `3` | `digit`: overwrite is on, so replace | `3` | 7 | `+` | false |
| `=` | `equals`: `settle(apply(7, 3, '+'))` | `10` | null | null | true |

Other paths through the same function:

- `7 + 3 +` calculates `10` straight away and stores it. That's how chained calculations work.
- `5 / 0 =` produces `Infinity`. `format` turns that into `'Error'` and the state becomes `errorState`. In that state, the first line of `reduce` ignores every action except `clear`.

### Why it's split this way

- **`Calculator.tsx`** only handles input and display. It turns clicks and keys into actions and shows `state.display`. It contains no math.
- **`calc.ts`** only handles the logic, as a function from state and action to the next state. It has no React, page or event code.

That split lets [calc.test.ts](../web/src/calc.test.ts) test the calculator by calling `reduce` directly, with no browser or rendering.

`StrictMode` deliberately runs components and effects twice in development to catch bugs, which is why the keydown listener is added, removed and added again. This doesn't happen in the production build.

## 7. Deep dive: `calc.ts`

### 7.1 What `export` does

Each `.ts` file is a **module**, and everything declared in it is private to that file by default. `export` makes a declaration visible to other files, which can then `import` it.

```ts
// calc.ts
export function reduce(...) { ... }   // other files can import this
function apply(...) { ... }           // only calc.ts can use this
```

```ts
// Calculator.tsx
import { type Action, type Op, initialState, reduce } from './calc';
//       ✅ all exported          ❌ `apply` or `errorState` here would be a compile error
```

Two details:

- **Exported types disappear at build time.** `type` declarations exist only for TypeScript's checks, so after compilation there's nothing left to import. That's why the import writes `type Action` explicitly; this project's `verbatimModuleSyntax` setting requires it. Exported `const` and `function` declarations do become real JavaScript exports.
- **There are two kinds of export.**
  - *Named* exports, which `calc.ts` uses (`export function reduce`), are imported with braces: `{ reduce }`.
  - A *default* export, which [Calculator.tsx](../web/src/Calculator.tsx) uses (`export default function Calculator`), is limited to one per file and imported without braces: `import Calculator from './Calculator'`.

### 7.2 When to use `export`

Export what other files need, and keep everything else private. The private parts can then change without breaking any other file.

| Name | Exported? | Used outside calc.ts by |
| --- | --- | --- |
| `Op` (type) | ✅ | `Calculator.tsx`, for the button and key tables |
| `CalcState` (type) | ✅ | `calc.test.ts` |
| `Action` (type) | ✅ | `Calculator.tsx`, `calc.test.ts` |
| `initialState` | ✅ | `Calculator.tsx` (`useReducer`), tests |
| `reduce` | ✅ | `Calculator.tsx` (`useReducer`), tests |
| `format` | ✅ | **No one.** It's exported, but nothing imports it. |
| `MAX_DIGITS` | ❌ | Internal setting |
| `errorState` | ❌ | Internal; reached only through `reduce` |
| `apply`, `digitCount`, `settle` | ❌ | Internal helpers that `reduce` calls |

The rest of the app only needs **`reduce` and `initialState`**, plus the types that describe them. That's the whole public surface of `calc.ts`. `format` is the exception: it was probably exported so it could be tested directly, but no test does that. You could remove the `export` or add tests for it.

### 7.3 Words used in `calc.ts`

**Reserved words in JS/TS** (you can't use these as names):

| Word | Meaning |
| --- | --- |
| `export` | Make a declaration importable |
| `const` | Declare a name that can't be reassigned |
| `function` | Declare a function |
| `return` | Leave a function and send back a value |
| `if` | Run code only when a condition is true |
| `switch` / `case` | Pick a branch by comparing one value against several options |
| `null` | "Deliberately no value" (for example, `accumulator: null` before an operator is pressed) |
| `true` / `false` | Boolean values |

**TypeScript-only words:**

| Word | Meaning |
| --- | --- |
| `type` | Declare a type alias (section 7.4). It's a *contextual* keyword, special only in that position, so a variable can still be named `type`. |
| `number`, `string`, `boolean` | Built-in types used in annotations like `n: number` |

**Not keywords, but easy to mistake for them:**

- `Number`, `String`, `Math` and `Object` are built-in global *objects* (`Math.abs`, `Number.isFinite`, `Object.is`).
- `'Error'` is just a string value here, not the built-in `Error` class.

**Symbols worth knowing:**

- `:` adds a type annotation (`n: number`).
- `|` means "one of" in a type (`'+' | '-'`).
- `...` is *spread*: it copies an object's properties into a new object.
- `===` and `!==` compare strictly, without type conversion. Always prefer them to `==` and `!=`.
- `&&` and `||` mean "and" and "or".
- `` `${x}` `` is a template string with `x` inserted.
- `/** … */` is a doc comment, which editors show when you hover over the name.

### 7.4 Syntax of `type`, `const` and `function`

#### `type`: give a name to a shape of data

```
type  Name  =  <type expression> ;
```

All three forms used in this file:

```ts
// (a) Union of literal values: an Op can only be one of these four strings.
export type Op = '+' | '-' | '*' | '/';

// (b) Object type: the properties a CalcState must have, and each one's type.
export type CalcState = {
  display: string;
  accumulator: number | null;   // a number OR null
  pendingOp: Op | null;         // reuses the Op type
  overwrite: boolean;
  error: boolean;
};

// (c) Union of object types (a "discriminated union"): every variant has a `type`
//     field holding a different string, so TypeScript can tell which one it has.
export type Action =
  | { type: 'digit'; value: string }   // the leading | is optional, for neat alignment
  | { type: 'decimal' }
  | { type: 'op'; value: Op }
  ...
```

Form (c) is what makes `reduce` safe. Inside `case 'digit':`, TypeScript knows `action` is the `digit` variant, so `action.value` is a `string`. Inside `case 'decimal':`, writing `action.value` is a compile error, because that variant has no `value`.

#### `const`: a name bound to a value

```
const  name  [: Type]  =  value ;
```

```ts
const MAX_DIGITS = 12;                              // type worked out automatically: number
export const initialState: CalcState = {            // annotated: TypeScript checks the
  display: '0', accumulator: null, ...              // object has exactly CalcState's fields
};
const errorState: CalcState = { ...initialState, display: 'Error', error: true };
//                              └ copy all fields ┘ └ then override these two ┘
```

`const` means the *name* can't be pointed at something else (`MAX_DIGITS = 13` is an error). It doesn't freeze the object's contents. This code never changes objects anyway: it always builds new ones with `{ ...state, display: … }`, and React relies on that to notice changes.

#### `function`: a named, reusable block of code

```
function  name ( param: Type, param: Type ) : ReturnType  {  body  }
```

```ts
function apply(a: number, b: number, op: Op): number {
//       name  ─────── parameters ────────   ↑ return type
  switch (op) {
    case '+': return a + b;
    case '-': return a - b;
    case '*': return a * b;
    case '/': return a / b;
  }
}
```

TypeScript checks both the calls (`apply(1, 2, '%')` is a compile error, because `'%'` isn't an `Op`) and the returns. `apply` has no `default:` and no final `return`. That's allowed because TypeScript can see that the four cases cover every possible `Op`. If you add `'^'` to `Op` and forget to handle it here, you get a compile error ("Function lacks ending return statement"). The same happens in `reduce` if you add a new `Action`.

### 7.5 Is `errorState` a keyword?

No. `errorState` is an **identifier**, a name the author chose. You could rename it `oops` everywhere in the file and nothing would change. The same goes for `initialState`, `reduce`, `apply`, `MAX_DIGITS`, `CalcState` and the other names.

The naming styles follow common conventions; the language doesn't require them:

- `camelCase` for values and functions: `errorState`, `digitCount`
- `PascalCase` for types: `CalcState`, `Action`
- `UPPER_SNAKE_CASE` for fixed settings: `MAX_DIGITS`

To tell whether a word is a keyword in VS Code, **Cmd+click** it or press **F12**. If it jumps to a declaration, it's an identifier someone defined. Reserved words like `const` and `return` have no declaration to jump to.

## 8. TypeScript and TSX for Java developers

These are the differences most likely to catch out a Java developer, roughly in order of how often they cause confusion.

### The type system

**1. Types don't exist when the code runs.** TypeScript checks types and then removes them all, leaving plain JavaScript. Java keeps class information at runtime (`instanceof`, reflection); TypeScript keeps nothing.

- You can't write `if (x instanceof CalcState)`, because `CalcState` no longer exists after compilation.
- Data from outside your code (an API response, `JSON.parse`) is *not* checked when it arrives. Declaring it as `CalcState` is only a promise to the compiler. Validate it yourself, or with a library such as `zod`.

**2. Types are matched by shape, not by name.** In Java, a class must declare `implements Foo` to count as a `Foo`. In TypeScript, any object with the right fields counts:

```ts
const s: CalcState = { display: '0', accumulator: null, pendingOp: null, overwrite: true, error: false };
// No class, no constructor, no "implements". It matches CalcState's shape, so it IS one.
```

That's why `calc.ts` has no classes at all. Data is described with `type`, and behaviour lives in plain functions. TypeScript does have classes, but modern React code rarely uses them.

**3. Unions replace inheritance.** In Java 21 you'd model `Action` as a `sealed interface` with one `record` per action and use a pattern-matching `switch`. TypeScript's `Action` union with `switch (action.type)` is the same idea in less code. Inside each `case`, TypeScript knows which variant it's dealing with (this is called *narrowing*). Narrowing also happens after checks such as `if (x !== null)` and `typeof x === 'string'`.

**4. `null` is part of the type.** With `strict: true` (on in this project), `number` does *not* include `null`. You have to write `number | null`, as `accumulator` does, and TypeScript then makes you check for `null` before doing arithmetic with it. So most of Java's `NullPointerException` problems become compile errors. One complication is that JavaScript has **two** empty values, `null` and `undefined`. Related syntax you'll see a lot:

```ts
user?.address?.city      // safe navigation: stops at the first null/undefined (instead of throwing)
value ?? 'default'       // use the right side only if value is null/undefined
name?: string            // in a type: an optional field (may be missing, i.e. undefined)
```

**5. `any` turns off type checking, so use `unknown` instead.** `any` accepts anything, stops all checks, and spreads to whatever it touches. `unknown` is the safe version: like a Java `Object`, you have to check it before using it.

### Values and runtime behaviour

**6. `number` is always a 64-bit floating-point number.** There's no `int`, `long` or `BigDecimal`:

- `7 / 2` is `3.5`. Use `Math.trunc(7 / 2)` for integer division.
- `0.1 + 0.2` is `0.30000000000000004`, which is exactly why [calc.ts](../web/src/calc.ts) has `format()`.
- `5 / 0` gives `Infinity` rather than throwing an exception, so `format` checks `Number.isFinite`.
- For money, store whole cents as integers or use a decimal library. `bigint` exists for very large integers.

**7. Equality.** Always use `===` and `!==`, because `==` converts types first (`'1' == 1` is true).

- For objects, `===` compares *references*, like Java's `==`. There's no `equals()` or `hashCode()`, so `{a: 1} === {a: 1}` is `false`.
- A `Map` or `Set` keyed by objects only matches the same object instance.
- React depends on this: it detects a state change because `reduce` returns a *new* object.

**8. Truthy and falsy values.** `if (x)` works on any type. `0`, `''`, `NaN`, `null`, `undefined` and `false` all count as false, and everything else counts as true. That catches people out: `if (count)` is skipped when `count` is `0`. `Calculator.tsx` uses this deliberately: `data-error={state.error || undefined}` leaves the attribute off entirely when there's no error.

**9. `const` vs `final`, and copying is shallow.** `const` is like `final`: the name can't be pointed at something else, but the object's contents can still change. For read-only *contents*, use `readonly` fields or `as const`. The `{ ...state, display }` spread copies only the top level, so nested objects are still shared between the copies.

**10. Functions are values.** You can store them in variables, pass them around and return them, like Java lambdas but without needing a functional interface. Arrow functions are everywhere:

```ts
onClick={() => dispatch(key.action)}           // a function passed as a prop
KEYS.map((key) => <button>…</button>)          // like stream().map(...).toList(), but directly on arrays
```

There's no overloading by parameter list. Use optional parameters or union types instead.

**11. JavaScript runs on a single thread.** There are no threads, `synchronized` blocks or thread pools. Waiting for I/O uses `Promise` with `async`/`await`, run by an *event loop*: an `await` pauses that function while other events run. Clicks and key presses in this app are handled the same way, one event at a time.

**12. A module is a file, not a package.** Imports use file paths (`'./calc'`, with no extension). There's no package-private visibility: a declaration is either exported or private to its file.

### TSX and React

**13. JSX is an expression, not a template.** `<button>…</button>` evaluates to a value that you can return, store or put in an array. Inside JSX:

- `{ }` holds a JavaScript expression (`{state.display}`). There's no `if` or `for`; use `cond && <X/>`, `a ? <X/> : <Y/>` and `.map()` instead.
- Attribute names differ from HTML: `className` instead of `class`, `htmlFor` instead of `for`, and camelCase events such as `onClick`.
- Lists need a `key` prop (`key={key.label}`) so React can match items between renders.

**14. A component is a function that runs again on every render.** `Calculator()` isn't an object constructed once; React calls it again every time state changes. Local variables are recreated each time. That's why state lives in `useReducer` and `useState`, and why `useCallback` and `useEffect` exist: to keep a value or effect stable across those repeated calls. Hooks (`use…`) must be called at the top level of the component, in the same order every time, never inside `if` statements or loops.

### Tooling

**15. The dev server doesn't check types.** `npm run dev` (Vite) strips the types and runs the code, so code with type errors still runs in the browser and may fail there. Type errors are only caught by:

- your editor's red underlines
- `npm run build`, which runs `tsc --noEmit` first

In Java, code with errors doesn't compile at all, so it's easy to expect the same here. Keep an eye on the editor, or run `npx tsc --noEmit --watch` in a spare terminal.

The ones that come up most in this code are 1 (types are removed), 2 (matching by shape), 3 and 4 (unions and `null`), 6 (`number`), 7 (equality) and 14 (components re-run).

## 9. AWS and CloudFormation: concepts and sequence

Steps 1–5 below have already happened on your machine. Steps 6–7 (bootstrap and deploy) haven't been run yet.

### Concepts you need first

| Term | What it is | Java analogy |
| --- | --- | --- |
| **AWS resource** | One piece of cloud infrastructure: a storage bucket, a CDN, a function, a permission role | An object instance |
| **CloudFormation** | AWS's service for creating infrastructure. You give it a **template** (JSON or YAML) listing the resources you want. It works out what to create, update or delete, does it in the right order, and rolls back if something fails. | Like a database migration tool, but for infrastructure: you describe the desired end state and it applies the changes |
| **Stack** | One deployed template and the resources it created, managed and deleted as a unit. Here: `CalculatorSiteStack`. | One deployable unit, like a single deployed application |
| **CDK** (Cloud Development Kit) | Lets you write TypeScript (or Java, Python and others) that *generates* the CloudFormation template, instead of writing long JSON by hand | Code that generates config, the way annotation processing generates code |
| **Construct** | A CDK class representing one or more resources (`new s3.Bucket(...)`). Some high-level constructs create several resources. | A class from a library you instantiate |
| **Synth** (synthesize) | Running your CDK code to produce the template plus the files to upload, written to `cdk.out/` | `javac` writing compiled output to `target/` |
| **Asset** | A local file or folder the stack needs in AWS (your site, Lambda code). CDK zips it and uploads it during deploy. | Bundled resources in a JAR |
| **Bootstrap** | A one-time setup per AWS account and region that creates a staging bucket and IAM roles for CDK deploys | Setting up a Maven repository before you can deploy to it |
| **Lambda** | A function that runs in AWS on demand, with no server for you to manage | — |
| **Custom resource** | A Lambda that CloudFormation calls during a deploy to do something it can't do itself, such as copying files into a bucket | A hook in a build pipeline |

The overall flow:

```
TypeScript (bin/, lib/) ──cdk synth──► cdk.out/ (template + assets) ──cdk deploy──► CloudFormation ──► real AWS resources
```

### Step 1: Write the source (Claude wrote these files)

| File | Goal |
| --- | --- |
| [lib/calculator-site-stack.ts](../infra/lib/calculator-site-stack.ts) | Describe *what* infrastructure to create, as a class `CalculatorSiteStack extends Stack` that creates constructs in its constructor |
| [bin/infra.ts](../infra/bin/infra.ts) | Entry point (like `main()`): create the CDK `App`, read the optional domain settings and create one stack instance in `us-east-1` |
| [cdk.json](../infra/cdk.json) | Tell the `cdk` command *how to run* your code (`"app": …`), and turn on CDK feature flags |
| [tsconfig.json](../infra/tsconfig.json) | TypeScript settings for type-checking `bin/` and `lib/` |
| [package.json](../infra/package.json) | Project name and npm scripts (`synth`, `deploy`, `destroy`…). The dependencies were added in step 2. |

### Step 2: Install tools and libraries (`npm install`)

| Command | Goal | Created |
| --- | --- | --- |
| `npm install aws-cdk-lib constructs` | The CDK library itself: every construct class (`s3.Bucket`, `cloudfront.Distribution`…) | `node_modules/`, `package-lock.json` |
| `npm install -D aws-cdk typescript ts-node @types/node` | `aws-cdk` is the **`cdk` command-line tool**. The others type-check and run TypeScript. | Added to the above |

This is like Maven downloading dependencies. `aws-cdk-lib` is the library your code uses; `aws-cdk` is the tool that runs it.

### Step 3: Type-check (`npm run typecheck`, i.e. `tsc --noEmit`)

This checks that the stack code compiles, without producing any files.

### Step 4: First synth attempt, which failed, and the fix

| Command | Result |
| --- | --- |
| `npx cdk synth` | `cdk` read `cdk.json` and tried `npx ts-node … bin/infra.ts`. `ts-node` crashed because it doesn't support TypeScript 7, leaving an empty `cdk.out/`. |
| `npm uninstall ts-node`, then `npm install -D tsx` | Replaced it with `tsx`, which runs TypeScript directly |
| Claude edited `cdk.json` | `"app"` changed to `"npx tsx bin/infra.ts"` |

### Step 5: Synth (`npx cdk synth`, or `npm run synth` from the root)

**Goal:** turn your TypeScript into a CloudFormation template plus the files to upload, *without touching AWS*. This step needs no AWS account.

What happens internally:

1. `cdk` reads `cdk.json` and runs `npx tsx bin/infra.ts`.
2. Your code runs: `new App()`, then `new CalculatorSiteStack(...)`, whose constructor creates each construct.
3. `BucketDeployment` points at `web/dist`, so **synth needs the web build to exist first**.
4. CDK converts the constructs into a template and writes everything to `cdk.out/` (see [section 2](#generated-cdkout)).

None of the Lambda code in `cdk.out/` was written by you or by Claude. It comes from inside `aws-cdk-lib` and was added because the stack uses `BucketDeployment` and `autoDeleteObjects: true`.

#### What the template contains

The ~140 lines of stack code produce **13 resources**:

| Resource (CloudFormation type) | Created by your code | Purpose |
| --- | --- | --- |
| `AWS::S3::Bucket` | `new s3.Bucket(...)` | Stores the site files |
| `AWS::S3::BucketPolicy` | Bucket settings plus OAC | HTTPS only, and only CloudFront may read |
| `AWS::CloudFront::OriginAccessControl` | `S3BucketOrigin.withOriginAccessControl` | Lets CloudFront sign its requests to the private bucket |
| `AWS::CloudFront::Distribution` | `new cloudfront.Distribution(...)` | The CDN: the public HTTPS URL, caching and the `index.html` fallback |
| `AWS::Lambda::Function` + `AWS::IAM::Role` + `Custom::S3AutoDeleteObjects` | `autoDeleteObjects: true` | Empties the bucket on destroy, because AWS won't delete a bucket that still has files in it |
| `AWS::Lambda::Function` + `AWS::IAM::Role` + `AWS::IAM::Policy` + `AWS::Lambda::LayerVersion` + `Custom::CDKBucketDeployment` | `new s3deploy.BucketDeployment(...)` | Copies `web/dist` into the bucket and clears the CloudFront cache on each deploy |
| `AWS::CDK::Metadata` | Added automatically | Anonymous CDK version info |

The template also has:

- 4 **Outputs** (`SiteUrl`, `DistributionDomainName`, `DistributionId`, `BucketName`), which are values printed after a deploy
- 1 **Parameter**, `BootstrapVersion`, which checks that the account has been bootstrapped

With a custom domain (`-c domainName=…`), synth also adds a certificate (`AWS::CertificateManager::Certificate`) and a DNS record (`AWS::Route53::RecordSet`).

### Step 6: Bootstrap (not run yet; once per account and region)

```bash
cd infra && npx cdk bootstrap aws://<account-id>/us-east-1
```

**Goal:** create the infrastructure CDK itself needs, deployed as a separate stack called `CDKToolkit`:

- a **staging S3 bucket**, `cdk-hnb659fds-assets-<account>-us-east-1`
- **IAM roles** that deploys use: `file-publishing-role`, `deploy-role`, `cfn-exec-role` and `lookup-role`

These are the names that appear in `manifest.json` and `assets.json`. `hnb659fds` is CDK's default identifier for this setup. Bootstrap writes nothing to your project folder.

### Step 7: Deploy (not run yet: `npm run deploy` from the root)

**Goal:** create the real resources in your AWS account.

1. `npm run build` rebuilds `web/dist`.
2. `cdk deploy` runs synth again, which refreshes `cdk.out/`.
3. **Publish assets:** using `file-publishing-role`, CDK zips each `asset.*` and uploads it, along with the template, to the staging bucket.
4. **Deploy the stack:** CDK asks CloudFormation to create or update `CalculatorSiteStack` from the template. CloudFormation, using `cfn-exec-role`, then:
   - creates the bucket, OAC, distribution, roles and Lambdas, in an order based on their dependencies
   - reaches `Custom::CDKBucketDeployment` and runs the Python Lambda, which copies the site zip from the staging bucket into **your** bucket and clears CloudFront's cache
5. CloudFormation reports success and CDK prints the Outputs. You'd open `SiteUrl`.

Creating a CloudFront distribution for the first time usually takes several minutes. Later deploys only change what's different, and you can preview those changes with `npm --prefix infra run diff`.

### Afterwards: `npm run destroy` (`cdk destroy`)

CloudFormation deletes the stack's resources. When it reaches `Custom::S3AutoDeleteObjects`, the Node.js Lambda empties the bucket first so the bucket can be deleted. The bootstrap stack (`CDKToolkit`) stays, because it's shared by all CDK projects in that account and region.

### How the pieces depend on each other

| Step | Tool | Needs | Produces | Touches AWS? |
| --- | --- | --- | --- | --- |
| Write source | You or Claude | — | `bin/`, `lib/`, configs | No |
| `npm install` | npm | `package.json` | `node_modules/`, lock file | No |
| `npm run build` (web) | Vite | `web/src` | `web/dist/` | No |
| `cdk synth` | `cdk` + `tsx` | source, `node_modules`, `web/dist` | `cdk.out/` | No |
| `cdk bootstrap` | `cdk` | AWS credentials | `CDKToolkit` stack | **Yes, once** |
| `cdk deploy` | `cdk` → CloudFormation | everything above | `CalculatorSiteStack` and the live site | **Yes** |

To deploy, you need AWS credentials (set up with `aws configure` and checked with `aws sts get-caller-identity`). Then bootstrap, then run `npm run deploy`.

## 10. Project files and tools

`package.json`, `package-lock.json` and `tsconfig.json` appear in both `web/` and `infra/` because each folder is a **separate Node.js project** with its own dependencies, compiler settings and installed packages.

### 10.1 What each file does

#### `package.json`: the project file (like `pom.xml`)

You write it, and npm updates it when you install or uninstall packages. It contains:

| Field | Purpose | Java equivalent |
| --- | --- | --- |
| `name`, `version`, `private` | Identity. `private: true` stops it being published to the npm registry by accident. | `groupId`/`artifactId`/`version` |
| `dependencies` | Packages your code uses when it runs | `<scope>compile</scope>` |
| `devDependencies` | Tools needed only to build or test | `<scope>test</scope>`, `<scope>provided</scope>` |
| `scripts` | Named commands, run with `npm run <name>` | Maven goals or Gradle tasks |
| `type: "module"` (web only) | Treat `.js` files as modern ES modules (`import`/`export`) | — |

Versions are ranges. `"react": "^19.3.0"` means "19.3.0 or any later 19.x", but never 20, because a new major version can break things.

#### `package-lock.json`: the exact versions (like a Gradle lock file)

npm writes this file, and you never edit it. It records the **exact** version, download URL and checksum of every package, including the packages your packages depend on: 90 in `web` and 78 in `infra`. `package.json` says *"React 19.3 or newer"*; the lock file says *"exactly 19.3.x, from this URL, with this checksum"*.

**Why it matters:** without it, installing next month could pick up newer versions that behave differently. Always commit it. `npm ci` installs exactly what it lists.

#### `tsconfig.json`: TypeScript settings (like `maven-compiler-plugin` config)

It tells `tsc` and your editor:

- which files to check (`include`)
- which language version to target (`target`)
- which built-in APIs exist (`lib`, `types`)
- how imports are resolved (`module`, `moduleResolution`)
- how strict to be (`strict`, `noUnusedLocals`…)

Your editor reads it too; that's where the red underlines come from.

### 10.2 Why each module has its own copy

`web` and `infra` produce code that runs in **different places**, and they share no dependencies.

| | `web/` | `infra/` |
| --- | --- | --- |
| Code runs in | **A visitor's browser** | **Node.js on your machine**, only during synth or deploy |
| Produces | `web/dist` (the site) | `cdk.out/` (template and assets) |
| Main dependencies | `react`, `react-dom` | `aws-cdk-lib`, `constructs` |
| Dev tools | `vite`, `vitest`, `typescript`, `@vitejs/plugin-react`, `@types/react*` | `aws-cdk` (the `cdk` command), `tsx`, `typescript`, `@types/node` |
| Scripts | `dev`, `build`, `preview`, `test` | `synth`, `diff`, `deploy`, `destroy`, `bootstrap`, `typecheck` |

The two `tsconfig.json` files differ because the code runs in different places:

| Setting | `web` | `infra` | Why |
| --- | --- | --- | --- |
| `lib` | `ES2022`, `DOM`, `DOM.Iterable` | `ES2022` | Only browser code can use `document` and `window` |
| `types` | `vite/client` | `node` | Browser and Vite types vs Node types (`process`, `path`, `__dirname`) |
| `jsx` | `react-jsx` | (none) | Only `web` contains `.tsx` files |
| `module` / `moduleResolution` | `ESNext` / `bundler` | `NodeNext` / `NodeNext` | Vite resolves imports in `web`; Node.js does it in `infra` |
| `noEmit` | `true` | (not set) | In `web`, Vite produces the JS output. In `infra`, `tsx` runs the code and the `typecheck` script passes `--noEmit` itself. |

Keeping them separate means `aws-cdk-lib` (hundreds of MB) never ends up near your browser bundle, React never ends up in your infrastructure code, and each side can upgrade its own TypeScript and tools independently.

**The root [package.json](../package.json)** is *not* a parent POM. It has no dependencies, no lock file and no `node_modules`. It's only a set of shortcut scripts that run commands in the subfolders with `--prefix`:

```json
"build":  "npm --prefix web run build",          // = cd web && npm run build
"deploy": "npm run build && npm --prefix infra run deploy"
```

npm does have a feature for real multi-module setups, *workspaces*, which is closer to Maven modules. This project doesn't use it.

### 10.3 Why only `web` has `vite.config.ts`

Vite is the web app's **build tool and dev server**. Think of it as Maven plus a hot-reloading local server for front-end code. Only `web` needs it because:

- **Browsers can't run `.tsx`.** Something has to convert it to JavaScript, resolve the `import` statements and combine everything into a few files.
- **Production files should be small and cache-friendly.** Vite minifies them and adds hashes to the file names (`index-<hash>.js`).
- **Development should be fast.** `npm run dev` serves files on demand and updates the page as you save (*hot module replacement*).

`infra` needs none of that. Its code never leaves your machine; `tsx` runs the TypeScript directly in Node.js, once, during synth.

What [vite.config.ts](../web/vite.config.ts) sets:

| Setting | Effect |
| --- | --- |
| `plugins: [react()]` | Converts JSX and enables hot reload for React components |
| `server.host: true`, `port: 5173` | Makes the dev server reachable from other machines and from Docker |
| `build.outDir: 'dist'` | Where the production build goes; `infra` reads it from there |
| `build.sourcemap: true` | Produces `.js.map` files, which then get published |

Vitest, the test runner, also reads this file, so tests use the same plugins and settings as the app.

### 10.4 `npm`, `npx` and `cdk`

#### `npm`: package manager and script runner (Maven/Gradle)

npm comes with Node.js (here, Node v24.15 and npm 11.12).

| Command | What it does | Used in this project |
| --- | --- | --- |
| `npm install` | Installs everything in `package.json` into `node_modules/` and updates the lock file | Initial setup (with `--cache` on this machine) |
| `npm install <pkg>` / `-D <pkg>` | Adds a dependency or dev dependency | `react`, `vite`, `aws-cdk-lib`… |
| `npm uninstall <pkg>` | Removes one | `ts-node` |
| `npm ci` | Clean install of *exactly* what the lock file lists; fails if it doesn't match `package.json` | The `Dockerfile`. Best for CI. |
| `npm run <script>` | Runs a script from `package.json` | `npm run build`, `npm run synth` |
| `npm test` | Shortcut for `npm run test` (`npm start` works the same way) | |
| `npm --prefix <dir> …` | Runs npm as if inside `<dir>` | The root scripts |
| `npm run <script> -- <args>` | `--` passes the extra arguments on to the script's command | `npm --prefix infra run deploy -- -c domainName=…` |

Inside `npm run`, `node_modules/.bin` is **added to the command search path**, so scripts can just say `vite`, `tsc` or `cdk`. These tools are installed locally in each project:

- `web/node_modules/.bin`: `vite`, `vitest`, `tsc`…
- `infra/node_modules/.bin`: `cdk`, `tsx`, `tsc`…

#### `npx`: run a package's command

`npx <command>` looks for the command in the current project's `node_modules/.bin` and runs it. If it isn't installed there, npx offers to **download it temporarily** and run it.

- Use it to run a project's tool directly in a terminal: `cd infra && npx cdk synth`.
- `cdk.json` uses it too: `"app": "npx tsx bin/infra.ts"`.

**Where `cdk` is installed matters.** `cdk` is **not installed globally** on your machine (`which cdk` finds nothing). It exists only in `infra/node_modules/.bin`. So:

- Typing `cdk synth` in a terminal fails with "command not found".
- `npx cdk synth` works when run **inside `infra/`**.
- `npm run synth` works from anywhere, because npm adds `.bin` to the search path.

#### `cdk`: the CDK command-line tool (from the `aws-cdk` package)

It runs your app (using the `"app"` setting in `cdk.json`) and talks to AWS.

| Command | What it does | Needs AWS credentials? |
| --- | --- | --- |
| `cdk synth` | Runs your code and writes the template and assets to `cdk.out/` | No |
| `cdk diff` | Runs synth, then compares the result with what's deployed, showing what would change before you deploy | Yes |
| `cdk bootstrap` | One-time setup of the staging bucket and roles in an account and region | Yes |
| `cdk deploy` | Runs synth, uploads assets, then creates or updates the stack through CloudFormation | Yes |
| `cdk destroy` | Deletes the stack and its resources | Yes |
| `-c key=value` | Passes a setting that your code reads with `tryGetContext` | — |

All of these are also available as `infra/package.json` scripts, which is why the README uses `npm run …` rather than calling `cdk` directly.

### 10.5 How the tools call each other

```
npm run deploy                          (root package.json)
 ├─ npm --prefix web run build
 │    └─ tsc --noEmit && vite build     (web/node_modules/.bin, reads web/tsconfig.json + vite.config.ts)
 └─ npm --prefix infra run deploy
      └─ cdk deploy                     (infra/node_modules/.bin)
           └─ npx tsx bin/infra.ts      (from cdk.json "app" → writes cdk.out/)
           └─ upload assets + CloudFormation
```

## 11. Maven vs Gradle vs npm

Where it helps, the npm column uses this project's own files and commands.

### Concepts

| Concept | Maven | Gradle | npm |
| --- | --- | --- | --- |
| Runtime | JVM | JVM | Node.js (browser for front-end output) |
| Project file | `pom.xml` (XML, declarative) | `build.gradle` / `build.gradle.kts` (Groovy/Kotlin code) | `package.json` (JSON) |
| Project identity | `groupId:artifactId:version` | `group`, `name`, `version` | `name` (optionally `@scope/name`), `version` |
| Public registry | Maven Central | Maven Central (uses Maven repos) | npmjs.com registry |
| Package unit | Artifact (JAR/WAR) | Artifact (JAR/WAR) | Package (`.tgz` tarball) |
| Where dependencies live | Shared: `~/.m2/repository` | Shared: `~/.gradle/caches` | **Per project: `node_modules/`** (plus a download cache in `~/.npm`) |
| Version spec | Exact by default (`1.2.3`); ranges like `[1.0,2.0)` are rare | Exact, or dynamic `1.+` | Ranges by default: `^19.3.0` (same major), `~19.3.0` (same minor) |
| Locking exact versions | Not needed (versions are already exact) | Optional: `gradle.lockfile` | **`package-lock.json`** (always; commit it) |
| Version conflicts | "Nearest wins": one version per artifact | "Highest wins": one version per artifact | **Multiple versions can coexist**, nested in `node_modules` |
| Build model | Fixed **lifecycle phases** with plugin goals bound to them | **Task graph** (tasks depend on tasks) | **Scripts**: named shell commands, with no built-in lifecycle |
| Extending the build | Plugins in `<build><plugins>` | Plugins in a `plugins {}` block | No plugin system: tools are dev dependencies, each with its own config file (`vite.config.ts`, `tsconfig.json`) |
| Multi-module | Parent POM with `<modules>` | `settings.gradle` with `include` | **Workspaces** (`"workspaces"` in the root `package.json`). *This project uses separate projects plus `--prefix` instead.* |
| Pinning the tool version | Maven Wrapper `mvnw` | Gradle Wrapper `gradlew` | `engines` / `packageManager` fields, `.nvmrc` (not used here) |
| Config and credentials | `~/.m2/settings.xml` | `gradle.properties` | `.npmrc` |

### Dependency scopes

| Purpose | Maven | Gradle | npm |
| --- | --- | --- | --- |
| Needed to compile and run | `compile` (default) | `implementation` (or `api` to expose to consumers) | `dependencies` (`react`, `aws-cdk-lib`) |
| Needed at runtime only | `runtime` | `runtimeOnly` | (no equivalent: `dependencies`) |
| Provided by the environment | `provided` | `compileOnly` | `peerDependencies` (the host project must supply it) |
| Tests or build tools only | `test` | `testImplementation` | `devDependencies` (`vite`, `vitest`, `typescript`, `aws-cdk`) |
| Optional | `<optional>true</optional>` | — | `optionalDependencies` |

### Files and output

| | Maven | Gradle | npm (this project) |
| --- | --- | --- | --- |
| Build definition | `pom.xml` | `build.gradle(.kts)`, `settings.gradle` | `package.json` |
| Lock file | — | `gradle.lockfile` (opt-in) | `package-lock.json` |
| Compiler config | `maven-compiler-plugin` in the POM | `java { toolchain {} }` | `tsconfig.json` |
| Bundler/packager config | `maven-jar-plugin`, `maven-shade-plugin` | `jar {}`, Shadow plugin | `vite.config.ts` (web only) |
| Build output folder | `target/` | `build/` | Set by the tool: `web/dist/`, `infra/cdk.out/` |
| Installed dependencies | `~/.m2/repository` (shared) | `~/.gradle/caches` (shared) | `node_modules/` (per project; `web` 73 MB, `infra` 240 MB) |
| Command-line tools from dependencies | — | — | `node_modules/.bin/` (`vite`, `tsc`, `cdk`, `tsx`) |
| Source layout | Fixed convention: `src/main/java`, `src/test/java` | Same convention | No convention: `src/` by habit, with tests often next to the source (`calc.test.ts`) |

### Commands

| Task | Maven | Gradle | npm |
| --- | --- | --- | --- |
| Install/resolve dependencies | (automatic during any build) | (automatic during any build) | `npm install` |
| Exact install from the lock file (CI) | (automatic) | `--dependency-verification` / locks | `npm ci` |
| Add a dependency | Edit `pom.xml` | Edit `build.gradle` | `npm install react` (edits `package.json` for you) |
| Add a test/dev dependency | Edit `pom.xml`, `<scope>test</scope>` | `testImplementation …` | `npm install -D vitest` |
| Remove a dependency | Edit `pom.xml` | Edit `build.gradle` | `npm uninstall ts-node` |
| Compile | `mvn compile` | `gradle compileJava` | `tsc` (here `tsc --noEmit` only type-checks) |
| Run tests | `mvn test` | `gradle test` | `npm test` |
| Run one test | `mvn test -Dtest=CalcTest` | `gradle test --tests CalcTest` | `npx vitest run calc.test.ts` |
| Skip tests | `-DskipTests` | `-x test` | (n/a: scripts only run what you list) |
| Package/build | `mvn package` | `gradle build` / `gradle jar` | `npm run build` (runs Vite) |
| Run the app locally | `mvn exec:java`, `mvn spring-boot:run` | `gradle run`, `gradle bootRun` | `npm run dev` |
| Clean | `mvn clean` | `gradle clean` | Nothing built in: `rm -rf dist node_modules` |
| Run a custom task | `mvn plugin:goal` | `gradle myTask` | `npm run <script>` (`npm run synth`) |
| Run a tool directly | `mvn <plugin>:<goal>` | `./gradlew <task>` | `npx <tool>` (`npx cdk synth`) |
| Pass arguments through | `-Dprop=value` | `-Pprop=value` / `--args` | `npm run deploy -- -c domainName=…` |
| Run in another module | `mvn -pl infra …` | `gradle :infra:task` | `npm --prefix infra run …` (or `-w infra` with workspaces) |
| Dependency tree | `mvn dependency:tree` | `gradle dependencies` | `npm ls` (`npm ls --all` for everything) |
| Check for newer versions | `mvn versions:display-dependency-updates` | Versions plugin | `npm outdated` |
| Security audit | OWASP dependency-check plugin | Same, via plugin | `npm audit` (built in) |
| Install locally for other projects | `mvn install` | `gradle publishToMavenLocal` | `npm link` / `npm pack` |
| Publish to the registry | `mvn deploy` | `gradle publish` | `npm publish` (blocked here by `private: true`) |
| Offline build | `mvn -o` | `--offline` | `--offline` / `--prefer-offline` |

### The main differences in practice

1. **npm has no build lifecycle.** `npm run build` runs whatever command the `build` script contains (here `tsc --noEmit && vite build`). There's no built-in compile → test → package sequence; scripts chain steps with `&&`.
2. **Dependencies are installed per project, and versions are ranges.** That's why the lock file matters much more in npm than in Maven, and why there are two separate `node_modules/` folders (73 MB + 240 MB) instead of one shared `~/.m2`.
3. **Multiple versions of the same package can coexist.** Maven and Gradle pick one version of a library; npm can install several, each nested where it's needed. You rarely get version-conflict errors, but the dependency tree gets bigger.
4. **Tools are ordinary dependencies.** In Maven, `maven-compiler-plugin` is part of the build system. In npm, `typescript`, `vite` and `aws-cdk` are just dev dependencies whose command-line tools live in `node_modules/.bin`. Scripts or `npx` run them, and each one is configured by its own file.
5. **Adding a dependency is a command, not an edit.** `npm install <pkg>` updates `package.json` and the lock file together. You *can* edit `package.json` by hand, but then you have to run `npm install` to update the lock file.
